# Main Investigation Platform v5 — sensor feedback release

This is an additive upgrade of the supplied v4 application. Run the existing migrations followed by `drizzle/0004_v5_sensor_feedback.sql` before serving v5. Back up the D1 database first. Existing v4 ingestion (`1.0`/`1.1`) and native event (`1.0`) payloads remain accepted; newly registered modules use event contract `2.0`. Keep each module's separate key in `MODULE_API_KEYS`, including `form_submitter` when installed. The Sites access token remains separately required for private deployments.

## Key change: observations do not imply a job

Publishing `site.discovered` stores an event without automatically creating `INVESTIGATE_SITE`. To request work, set `payload.request_investigation: true` with both a resolvable `investigation_id` and a site `entity_id`. For full triage, send `site.triaged` with `payload.outcome` (`observed`, `triaged`, `promoted`, `dismissed`, or `inconclusive`), `confidence` (0–1), `indicator_categories`, `evidence_refs`, `discovery_path`, and `request_downstream`. Only `promoted` plus `request_downstream: true` can route a triage event. Retrieve durable triage history with `GET /api/v1/triage?module=site_finder&entity_id=...`. A missing entity or investigation is recorded without routing.

A `wallet.observed` event does not become `wallet.validated` simply because confidence is high. A validating module must explicitly publish `wallet.validated` with its method and supporting evidence in provenance/payload. This protects the wallet analysis queue from unsupported chain claims.

## Subscriptions and discovery feedback

Register a module with `supported_event_types`, for example Site Finder can subscribe to `site.investigated`, `wallet.validated`, and `relationship.discovered`. The event inbox stores deliveries until acknowledged:

- `GET /api/v1/modules/{module}/events?limit=50` returns pending deliveries, including their `delivery_id`.
- `POST /api/v1/modules/{module}/events/{delivery_id}` acknowledges successful consumption. Repeat reads until acked; process by event ID idempotently. A reconnection resumes pending deliveries.
- `POST /api/v1/modules/{module}/metrics` upserts a complete metric window. Supply technique, campaign, UTC window_start/window_end, nonnegative numeric metrics, and provenance. `GET` returns the latest 100 windows. Metrics reflect discovery usefulness, not a maliciousness verdict.

The event ID is idempotent; reuse with different content returns HTTP 409. The current inbox is a durable pull subscription, suitable for workers that reconnect; it is not a live WebSocket push.

## Reporting

`form_submitter` may register `report-preparation`. A `report.ready` event queues `PREPARE_REPORT` only if `validation_passed` and `review_approved` are both true, and an investigation and entity are identified. Other report state events record progress; `report.submitting` alone does not imply completion. Only an explicit `report.completed` records a verified outcome. Form submission itself is the separate module's responsibility.

## Scope and remaining integration work

This release adds the contract and routing foundation, the three additive storage models, and SDK methods for event delivery and metrics. It preserves existing investigation, evidence, and job handling. It does not yet provide a full v5 investigation workspace, webhook delivery, automatic downstream metric attribution, comprehensive role-scoped authorization, or all requested failure and concurrency end-to-end tests. Review these gaps before treating this as a complete production rollout.
