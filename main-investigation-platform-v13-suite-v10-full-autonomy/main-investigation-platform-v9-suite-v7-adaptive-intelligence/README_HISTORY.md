# Main Investigation Platform v5 · Operations

> **Autonomous Investigation Director (suite v5 integration candidate).** Main maintains durable objectives, reasoned safe actions, bounded provider recovery and an investigation briefing. Existing wallet validation, evidence requirements and exact-content approval remain. Apply additive migration `0016_investigation_director.sql`; see `V5_DIRECTOR_UPGRADE.md` and `V5_INVESTIGATION_DIRECTOR_REPORT.md` for verified behavior and outstanding release gates. Tests: `npm run test:director`.

> **Autonomous wallet discovery & reporting (suite v4).** Browse a site you are investigating (log in yourself if it needs it) with Wallet Logger 0.9 switched on. The Logger only watches what your browser shows, including dynamic pages, modals, tabs, inputs, copy buttons, QR codes, Shadow DOM, page scripts and network responses. It sends each sighting to Main as a classified observation: deposit, withdrawal, example, history, contract, unrelated or unknown. Main merges sightings into one candidate per wallet. Wallet Investigator validates every candidate with real checksums and never guesses an EVM network. Valid deposit wallets are analysed within the wallet budget. Main then builds the report by itself and shows **Ready to report** in Site Finder's Investigate view and in Form Submitter. You review it once and press **Approve & Submit**. The approval covers exactly that content and that destination; if either changes, you are asked again. Form Submitter files the report once and stops for you at a sign-in or CAPTCHA. Apply migration `0015_wallet_pipeline.sql` (additive) and reload the Logger extension. See `V4_WALLET_RELEASE_REPORT.md` (benchmark wins *and* losses) and `integrations/crypto-wallet-logger-v08/README.md`. Tests: `node scripts/run-tests.mjs wallet-pipeline`.

> **Site Finder v3 · discovery pursuit & campaign hunting.** Site Finder now runs *hunts*: one clue grows into a bounded, multi-pivot search that follows the most informative public artifacts, drops dead branches with a reason and stops when it runs dry. In Main, Site Finder has three tabs — **Find sites | Investigate | Hunts** — and every candidate says *Found this because…* with a readable chain. Operation Hunter and completed investigations can start hunts ("Looking for new deployments related to Operation X"); these bring candidates, never relationships — the same kit is never treated as the same operator. Apply migration `0014_finder_hunts.sql` (additive). See `SITE_FINDER_V3_RELEASE_REPORT.md` (benchmark wins *and* losses) and `integrations/site-finder-v07/docs/PURSUIT.md`.

> **Unified investigation suite + Site Finder next generation.** Main now opens on five tools: Site Finder (discover and investigate), Wallet Investigator, Wallet Logger, Form Submitter and Operation Hunter. Coordination views live under Advanced, and the site, wallet or operation you are working on follows you between tools. Site Finder 2.1 pivots from what it already knows and never spends a review slot on sites the suite already holds. Apply migration `0013_wallet_key_prefix.sql`. See `NG_RELEASE_REPORT.md`.

> **Operation Hunter upgrade:** Operation Hunter v2.0 is now a registered module (`operation_hunter`). The scheduler asks it to reconstruct the operation behind campaigns and wallet-bearing sites; Hunter reports a living operation model and proposals, which become ordinary work items under your budgets. **v2 is built around one metric: how often the site put in front of you is actually worth checking.**

The primary screen is an investigation inbox. NEXT SITE → domain → OPEN SITE → SKIP / USEFUL → next. Everything else (scores, evidence, discovery paths, jobs, provenance) sits behind **Details** or under **Advanced**.

Your workflow: Site Finder discovers and filters in the background → the platform hands you one strong candidate → you open it (and log in yourself if needed) → CryptoWalletLogger collects evidence → the platform continues (site check, wallet capture/analysis, review, reporting) automatically. USEFUL also asks Site Finder for related sites; SKIP teaches it what not to bring you.

On the simulated v1-vs-v2 benchmark, precision went from ~40% to ~99% on the held-out split and from 33% to 100% on a stress split built to fool v2, while surfacing ~10× more useful sites. v1 was also sending records the platform rejected. See `V2_BENCHMARK_REPORT.md` (method and caveats), `V2_IMPLEMENTATION_REPORT.md` (what was wrong and what changed) and `V2_MIGRATION_NOTES.md` (upgrade, settings, rollback).

**v3 adds an AI investigation layer above the deterministic v2 platform.** When you mark a candidate USEFUL, an AI investigator understands the case, chooses one approved next action at a time, runs it through the existing modules, evaluates the result, pauses for you at a login/CAPTCHA/MFA wall (and resumes from the new evidence), and stops at a meaningful point within strict budgets. The model can only act through typed, permission-controlled capabilities; every safety, provenance, dedup, budget and validation rule lives outside the model, and an AI conclusion never becomes evidence or a discovery-training label. Site Finder v3 additionally learns from what investigations actually find, not only from your clicks. The investigation screen stays simple — status, plain-language activity, the human step — with all telemetry behind **Advanced**. See `V3_IMPLEMENTATION_REPORT.md`, `V3_MIGRATION_NOTES.md`, `V3_BENCHMARK_REPORT.md` and `V3_TEST_REPORT.md`. The AI runs a deterministic planner unless a model provider is configured (`AI_PROVIDER`).

**v4 adds campaigns: the platform decides what is worth investigating next.**

- **Starting.** Start a campaign from any inbox site. The platform gathers the sites, wallets and infrastructure observably linked to it; shared hosting, templates or wallets are treated as relationships, never ownership.
- **Deciding.** A deterministic priority engine ranks every piece of safe work, collapses near-identical mirrors, tests explicit, disprovable hypotheses with bounded Site Finder pivots, and has a Reviewer challenge each action before it runs.
- **Running.** It runs the v3 investigator on what matters and stops when nothing left is worth doing or a budget is reached. Only sites that need you (a login, CAPTCHA, MFA or a report approval) pause, and nobody presses Next Site.
- **Learning.** It learns from observed results and your decisions, never from its own conclusions. Site Finder v4 learns which pivot strategies work in which context and backs off paths that stop paying.
- **Results.** On the v3-vs-v4 benchmark at equal budget, v4 found 17% more unique wallets with a third of the duplicate investigations, half the wasted module work and no inbox decisions. `V4_BENCHMARK_REPORT.md` also reports where v3 still covers more ground, when the budget is large.
- **Further reading.** `V4_IMPLEMENTATION_REPORT.md`, `V4_MIGRATION_NOTES.md`, `V4_BENCHMARK_REPORT.md` and `V4_TEST_REPORT.md`.

**v5 · Operations runs the whole system continuously: Observe → Discover → Prioritize → Campaign → Investigate → Correlate → Learn → Monitor → Revisit.**

- **Autonomous scheduler.** One global, leased scheduler turns Site Finder candidates, evidence gaps and observed changes into typed work items with explained, deterministic priorities. It enforces concurrency and global/module/provider budgets, retries with backoff, recovers from crashes without duplicating work, and pauses or resumes cleanly.
- **Global intelligence graph and temporal intelligence.** Every link cites its source row; generic hosting links nothing; correlation is never ownership. An unchanged observation is not new evidence; a real change (site gone or back, new hosting, deposit page appeared, wallet rotated) creates the right revisit or pivot. Sources disagreeing becomes a contradiction for a person, not a change.
- **Gaps, campaigns and learning.** Evidence gaps drive work and stop it when resolved. Campaigns form, merge and split only on graph evidence, with lineage. Learning uses observed outcomes only; experiments may only reorder work, by ±20%.
- **AI stays advisory.** An AI team (typed artifacts, no agent-to-agent commands), model routing across providers with deterministic fallback, replayable AI decisions and a dry-run simulator, both of which execute nothing.
- **Operator Workspace.** Operations, Campaigns, Investigations, Discovery, Intelligence (interactive graph) and one Human Tasks queue; a command bar that compiles into the same typed policy; notifications that are deduplicated.
- **Site Finder v5.** Continuous, restart-safe discovery cycles with source rotation, novelty and ecosystem saturation, aging/rediscovery and DNS change watch.
- **Results.** On the v4-vs-v5 benchmark (same worlds, seeds and budgets), v5 revealed 57% more unique wallets with a third of the human interventions, at about the same module work per useful result. It also had more duplicate and dead-site jobs; see `V5_OPERATIONS_BENCHMARK_REPORT.md`.
- **Further reading.** `V5_OPERATIONS_IMPLEMENTATION_REPORT.md`, `V5_OPERATIONS_MIGRATION_NOTES.md` (upgrade and rollback), `V5_OPERATIONS_BENCHMARK_REPORT.md`, `V5_OPERATIONS_TEST_REPORT.md`; screenshots in `docs/screenshots/v5_*.png`.

Quick start: back up your data; `npm ci && npm run build && npm start` (applies migrations through 0011); start Site Finder as before (`integrations/site-finder-v07`, `python cli.py serve`). Tests: `npm test`, `npm run test:integration:v6`, `npm run test:v2`, `npm run test:v3`, `npm run test:v4`, `npm run test:v5`, or `npm run test:all`; `npm run benchmark:v4` runs the v3-vs-v4 benchmark and `npm run benchmark:v5` the v4-vs-v5 benchmark.

# Main Investigation Platform

This repository contains the five-module v6 platform and the v6.1 hardening work. **v6.1 has not passed its release gate.** Read [the audit](V6_1_AUDIT_REPORT.md), [test report](V6_1_TEST_REPORT.md), and [known limitations](V6_1_KNOWN_LIMITATIONS.md) before production use.

Modules: Site Finder, Site Investigator, CryptoWalletLogger, Wallet Investigator, and Form Submitter. The Main Platform owns routing, evidence preservation, planning, approvals, and reporting state. Specialized modules keep their own responsibilities. The shared contract is in `sdk/contracts/v6.json`; the current wire version is `3.0`, with explicitly supported legacy versions.

## Local validation

Requires Node.js >=22.13, Python 3, and the module-specific dependencies described in each integration README. Run `npm ci`, `npx tsc --noEmit`, `npm run lint`, `npm test`, `npm run test:integration:v6`, `npm run test:five-modules`, and `npm run build`. Tests use synthetic fixtures and localhost receivers. Neither the individual module tests nor a successful build establish a joined five-module production workflow.

Back up an existing database and check migration history before upgrading. The generated D1 binding points to ordered migrations `drizzle/0000` through `drizzle/0010`. After `npm run build`, `npm start` applies pending local migrations and serves the built application on `127.0.0.1:8787`; set `MIP_PERSIST_TO` to select another local persistence directory. Remote deployments must apply the same ordered migrations using the deployment's controlled migration step. Set individual module API keys and configure each module's Main Platform URL and module key. The built Worker registers a five-minute scheduled trigger for event recovery, feedback dispatch, and monitoring. External module servers remain separate supervised processes.

The multi-step test scripts (`test:integration:v6`, `test:v2`, `test:five-modules`, `test:joined:v61`, `test:startup:modules`, `benchmark`) run through `scripts/run-tests.mjs`, so they behave the same under PowerShell/cmd.exe as under a POSIX shell. Python steps use, in order: `MIP_PYTHON`, the repository `.venv` (`.venv\Scripts\python.exe` on Windows, `.venv/bin/python` elsewhere), an activated `VIRTUAL_ENV`, then `python`/`py -3` (Windows) or `python3` (elsewhere) on PATH. `npm run test:doctor` shows what was resolved and checks the toolchain; `npm run test:all` runs every group and prints PASS/FAIL per group. The `suite` group also clicks every control on every real page (`tests/ui-click-all.py`, server-rendered and hydrated, before and after a restart of Main) and takes the workflow's human decisions through the real buttons (`tests/ui-act.py`); `MIP_UI_SWEEP=0` skips the sweep, `MIP_REQUIRE_UI=1` turns a missing browser into a failure.

On Windows use PowerShell with Node.js and Python installed. Run `npm ci`, `npm run build`, apply D1 migrations using Wrangler as above, configure environment variables using your deployment's secure secret store, and run `npm start`. The built Worker cron requires a deployment that supports scheduled triggers; separately supervise all module processes. Do not commit API keys, provider credentials, form credentials, real evidence, or local databases.

See `V6_1_CANONICAL_CONTRACT.md` for the contract boundary and `V6_1_MIGRATION_NOTES.md` for upgrade and recovery notes.
