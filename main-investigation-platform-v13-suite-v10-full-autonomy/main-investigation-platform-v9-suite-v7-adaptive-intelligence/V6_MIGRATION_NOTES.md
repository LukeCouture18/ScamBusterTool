# v5 → v6 migration

1. Back up the existing D1 database and evidence bucket. Keep the v5 ZIP as a rollback artifact.
2. Apply `drizzle/0005_v6_planning.sql` once after migrations `0000` through `0004`. It adds tables and indexes without deleting v5 entities, investigations, jobs, events, evidence, or observations.
3. Deploy v6 code after applying the migration. Use fresh per-module keys, including `form_submitter` when registered. `platform` is an internal event source; do not issue its key to a standalone module.
4. Register v6 modules with schema `3.0` and their actual capabilities and subscriptions. v4 event `1.0`, v5 event `2.0`, and legacy ingestion `1.0`/`1.1` remain accepted. New ingestion uses `3.0`; financial amount fields in transactions must be decimal strings.
5. Configure investigation budget limits through `/api/v1/investigations/{id}/plan`; defaults are Quick 8 jobs, Standard 30, Deep 80, Continuous 40. This can be changed without rewriting old evidence.
6. If continuous monitoring is wanted while the UI is closed, configure an authenticated scheduler to call `POST /api/v1/monitoring/tick` at the desired cadence. The source package does not provision a cron trigger.
7. Verify a migration against a copy of production data, then exercise module registration, event delivery, job claim, and report gates before use. The included local migration and SQLite integration tests are repeatable checks.

Do not overwrite an existing v5 database with the test fixture. The ZIP excludes `node_modules`, local database state, and test credentials. Run `npm ci`, `npm test`, `npm run test:integration:v6`, and `npm run build` on a fresh checkout.

### Second-pass migration

Apply `drizzle/0006_feedback_delivery.sql` after `0005_v6_planning.sql`. It adds delivery attempt/lease/retry metadata to the existing v5 inbox; old subscriptions and acknowledgements remain intact. For feedback push, configure `FEEDBACK_SIGNING_KEY` as a strong secret and `FEEDBACK_WEBHOOK_ALLOWLIST` as a comma-separated list of exact HTTPS origins you control. A registered module may then set `metadata.feedback_webhook_url` within one of those origins; it must verify `X-Platform-Signature` over the exact request bytes and acknowledge the stable delivery ID. Without those settings, the existing durable pull/ack path continues to operate. A trusted scheduler must call `/api/v1/feedback/dispatch` to recover pending pushes and `/api/v1/monitoring/tick` for unattended monitoring; neither trigger is provisioned by this package.

Apply `drizzle/0007_monitoring_diffs.sql` after `0006`. Existing monitoring snapshots gain a default empty diff; new snapshots persist added and removed observation, evidence, and relationship versions. The migration is additive and retains all prior snapshots. `FEEDBACK_ALLOW_LOOPBACK_HTTP=true` permits HTTP only for an exact allowlisted localhost origin in isolated testing; keep it unset in deployed environments.

### Three supplied modules and local scheduler

- `integrations/site-finder-v07` is a derived copy of the supplied Site Finder source. Configure its existing `MAIN_PLATFORM_URL` and `MAIN_PLATFORM_TOKEN` for v6; it still sends 1.1 batches. It now attaches a public triage evidence record so v6 can safely promote a candidate. To opt into push feedback, configure `MAIN_PLATFORM_FEEDBACK_WEBHOOK_URL` with an HTTPS URL in the platform allowlist and set the same `MAIN_PLATFORM_FEEDBACK_SIGNING_KEY` at the receiver; the bundled receiver is `/api/integration/platform-feedback`.
- `integrations/site-investigator-v01` contains the supplied standalone investigator with its page insert fix. Run `integrations/site_investigator_bridge.py` with its source directory on `PYTHONPATH`, `MAIN_PLATFORM_URL` and `SITE_INVESTIGATOR_MODULE_KEY` set. The bridge claims public site jobs, keeps the worker lease alive, translates its SQLite results, and retries failures. It never performs authenticated work without that module's separate operator workflow.
- `integrations/crypto-wallet-logger-v08` is a derived extension. Set its **Main Platform endpoint** to `https://YOUR-PLATFORM/api/v1/compat/logger` and its API key to the `crypto_wallet_logger` module key. It sends passive native events; the adapter maps them to the canonical schema. Reinstall the derived extension to use stable deduplication and avoid queue truncation.
- Run `python3 integrations/local_scheduler.py` with `MAIN_PLATFORM_URL` and, for private Sites, `MAIN_PLATFORM_SITES_TOKEN`. It periodically invokes feedback recovery and monitoring. Keep it running as a service for unattended operation. The localhost test uses a synthetic receiver; no third-party webhook is needed.
- `integrations/wallet-investigator` and `integrations/form-submitter` now contain the supplied remaining sources and canonical workers. Set `MAIN_PLATFORM_URL`, `WALLET_INVESTIGATOR_MODULE_KEY`, and `FORM_SUBMITTER_MODULE_KEY` to enable them. Deterministic Wallet Investigator fixtures are disabled by default and only enabled in isolated tests with `WALLET_INVESTIGATOR_SYNTHETIC_FIXTURES=1`. Form completion requires an actual confirmation response; interrupted or ambiguous submission remains verification-unknown.
